# Deterministic security coverage inventory

This inventory records which security mistakes Autoreview can report from a
review snapshot and which additional checks have a concrete source signal.
The baseline is `b2e5b44` on `origin/main`. The transport rows record the
subsequent Node.js, Go, and Rust changes.

Weakness IDs come from the [CWE catalog](https://cwe.mitre.org/data/) and
[CWE Top 25](https://cwe.mitre.org/top25/). The [OWASP Top 10](https://owasp.org/Top10/2025/)
and [ASVS](https://asvs.owasp.org/) inform the coverage of web application and
operational controls.

## What the review engine can see

| Layer | Baseline evidence | Coverage boundary |
| --- | --- | --- |
| Syntax | [Builtin rule catalog](../crates/core/rules-builtin) contains security patterns for Go, Java, Kotlin, JavaScript, TypeScript, and Rust. TypeScript pattern rules are also emitted for TSX. [Pattern conformance](../crates/core/tests/rule_pack_conformance.rs) checks one expected match and a negative fixture per builtin pattern. | ast-grep must be installed. A property, method, or import spelling alone can match a lookalike. The byte-level [bidi scanner](../crates/core/src/analyzers/bidi_check.rs) runs independently of language grammars. |
| Symbols and dependencies between source files | [Symbol checks](../crates/core/src/analyzers/symindex_check.rs) report design issues such as message chains and feature envy. [Import evidence](../crates/core/src/analyzers/dataflow_check/keyed_imports.rs) and [framework binding helpers](../crates/core/src/analyzers/framework_checks/web.rs) give selected checks more precise identity. | These facilities do not provide general compiler-grade resolution of security API receivers or overloads. Architecture dependency budgets measure coupling. The optional TypeScript and Go probes serve selected result-flow checks. |
| Dataflow | [Builtin taint rules](../crates/core/src/analyzers/taint_rules.rs) model named sources, sinks, and limited sanitizer evidence. The [taint suite](../crates/core/tests/taint_rule_conformance.rs) exercises the registered rule pairs. [Keyed and result flow](dataflow-coverage-inventory.md) model selected paths, calls and result handling. | A registration for one framework does not transfer to another. Current taint configs omit sanitizer registrations. Helper or import support in call-order and result checks does not imply the same coverage for taint. Record analysis skips separately from clean fixtures. |
| Config | [GitHub Actions ref policy](../crates/core/src/analyzers/workflow_policy.rs) is opt-in via `artifactChecks.immutableGithubActionRefs`. [Artifact configuration](../crates/schema/src/artifact_config.rs) also enables selected migration, schema, locale, and outbox checks. | The policy reads direct workflow files and parsed job or step references. The other artifact checks do not establish deployment hardening, privileges, or secrets policy. |
| Dependency advisories | [Cargo audit adapter](../crates/core/src/analyzers/cargo_audit.rs) uses `--audit-rust-deps`, changed `Cargo.lock` files, and an offline local RustSec database for the default registry. | Findings depend on the available advisory snapshot and the lockfile. The repository has no equivalent builtin npm, Go, or JVM advisory adapter in this baseline. External analyzer diagnostics depend on installed tools and their configured checks. [RustSec](https://rustsec.org/) |
| Framework semantics | [Framework checks](../crates/core/src/analyzers/framework_checks.rs) include nearby correctness evidence such as JSON casts without runtime validation, Prisma transaction ownership, Go handler context, and Spring checks. [Rust SQL review](../crates/core/src/analyzers/rust_review/sql.rs) recognizes selected SQLx and rusqlite constructions as security findings. | Each check has its own supported API and proof. Neighboring correctness findings do not establish injection, authorization, or policy coverage. |

In the tables, **covered** means the named slice has a builtin detector.
**Partial** means a related detector exists but leaves the proposed slice open.
**Gap** means no dedicated builtin was found for the proposed slice. **High**
confidence requires a resolved API or configuration field with a documented
effect. **Medium** requires additional reachability, purpose, policy, or
environment evidence. Confidence applies to the proposed signal in each row.
Use inert fixture values and test the reported rule ID and location alongside
the negative control. Framework or deployment checks should use isolated tests
with local doubles or fixture configuration.

The first batch uses the native framework registry and parser, which allows the
same rule to run for JS, TS, and TSX without an ast-grep process. It recognizes
unescaped single- and double-quoted string values. Numeric coercion, aliases,
explicit imports of the Node process module, computed or escaped values, compound
assignments, environment files, deployment configuration, and shell commands
remain outside its scope. Local binding detection covers common parameters,
declarations, loop bindings, and imports. TypeScript-specific declarations
can remain unresolved. The check does not infer whether a
particular connection overrides the process default or whether a browser
supplies a different global `process`.

The resolved transport batch has these bounds:

- Node resolves default, namespace, and named client imports, along with direct
  CommonJS loads and const namespace bindings. It checks literal options and
  same-block const objects with no earlier use. It handles options-first HTTPS
  and TLS calls, HTTPS requests with a literal URL followed by options, and
  TLS connections with a literal port or socket path followed by options.
  A later spread or computed key can obscure the final value. Dynamic require,
  module patching, and other overloads are outside this analysis.
- Go recognizes same-block declarations with an explicit TLS type or a
  TLS config literal and directly declared parameters in the function body.
  It reports the write itself. Proving client use, custom verification, or
  later resets requires further flow analysis.
- Rust follows fluent calls and same-block builder locals. It also recognizes
  standalone native-tls setters in that block. A later false or dynamic setting
  masks an earlier true. Opaque methods, backend replacement, and unresolved
  mutations end the proof.

## Further implementation batches

1. **Output and dataflow boundaries.** Add DOM/React raw HTML and archive extraction sinks. Extend query/command/URL coverage one resolved framework API at a time, including guard and sanitizer tests.
2. **Workflow and dependency policy.** Add structured workflow shell interpolation and job permission checks. Evaluate one offline advisory adapter at a time with affected-range boundaries and missing-feed diagnostics.

### Bounds of the explicit settings checks

- JS, TS, and TSX checks resolve supported named and default imports, namespace
  calls, and direct or const CommonJS loads. Options may be inline objects or
  first-use same-block const objects. Later spreads or unknown computed keys
  can obscure an earlier setting. Dynamic bindings and defaults are outside
  the check.
- Go resolves direct golang-jwt v5 options on `NewParser`, `Parse`, and
  `ParseWithClaims`. It does not infer whether a later validator compensates
  for the parser option.
- Spring checks conventional `src/main/resources[/config]/application*.properties`
  files, including profile-specific names. It uses the final recognized value
  within one document. YAML, continuations, escaped keys, multi-document
  files, and runtime profile precedence are outside this check.
- The ECB check covers literal AES-128, AES-192, and AES-256 encryption
  variants in Node. It leaves legacy decryption, dynamic transformations, and
  configurable password-hashing costs outside this batch.
